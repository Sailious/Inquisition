## 产品概述

对 Inquisition 项目提交 `0a4a92a`（feat: 添加日志定时清理功能）及其后续提交做完整代码审查，逐文件判断其是否符合项目逻辑、是否存在缺陷或安全隐患、是否引入多余复杂度，并验证与既有架构和编码风格的一致性，最后给出"合理 / 需要修改 / 回退"的明确结论。

## 审查范围（已核实）

- `git rev-parse HEAD` 即为 `0a4a92a`，`0a4a92a..HEAD` 为空；`main` 上后续仅有 2 个 merge 提交（`9338b25`、`cd89117`），且 `git diff --stat 0a4a92a main` 为空，未引入任何内容变更。
- 实际审查对象就是 `0a4a92a`：新增 55 行、删除 0 行，涉及 `.env.example`、`application.yml`、`DynamicScheduleTask.java`。

## 核心审查结论

**结论：需要修改，但不需要回退。**

- 需要修改的理由：存在 1 个高危数据丢失风险（保留天数配置为 0 会物理清空整张 log 表，且功能默认开启）、1 个中危可靠性问题（无索引单次大删除形成长事务，阻塞单线程调度器，导致每 5 秒/6 秒的业务巡检停摆并误报设备离线告警）、1 个中危可观测性问题（异常日志吞掉堆栈）。
- 不回退的理由：改动仅 55 行、零新增依赖、零新增抽象层；配置分层与定时任务注册方式与既有 `price`/`admin` 配置段及前 7 个定时任务逐字同构；物理删除判定正确（项目未启用逻辑删除）；字段类型与 cron 方言均正确；且 log 表明文存储账号密码，缩短留存期本身就是安全加分项。
- 测试覆盖：为零。`src/test` 下仅 2 个冒烟测试，无任何调度或清理相关用例。

- 复用现有能力：`SchedulingConfigurer` + `addTriggerTask`、`BaseMapper` 物理删除、`@Value` 占位符链配置绑定。本次修复不引入任何新依赖或新抽象层。

## 实现方案

### 总体策略

保持"新增定时任务"这一实现路径不变，仅对边界条件、默认值、执行方式和日志做收敛式修复，把不可逆删除从"默认开启、单笔全量"改为"显式开启、分批限流、可观测"。

### 修复项与关键决策

**P0 高危：保留天数边界 + 默认开关**

- `if (logRetentionDays 小于 0)` 只拦了负数，配置为 0 时 `cutoff` 等于当前时刻，等价于清空整表。改为 `小于等于 0` 即视为非法并跳过清理。
- `enabled` 默认值由 `true` 改为 `false`，需三处同步：Java `@Value` 默认值、`application.yml` 占位符默认值、`.env.example` 示例值。理由：项目其他所有非推送类开关（`wx-pusher.enable`、`mail.enable`、`oss.enable`、`chfs.enable`）一律默认 `false`，物理删除更应遵循 opt-in 约定。

**P1 中危：分批删除 + 索引 + 调度隔离**

- 全项目实体从未声明过任何索引，actable 不会凭空创建，`WHERE time 小于 ?` 在生产库必然全表扫描，叠加长事务 next-key 锁会阻塞高频日志写入。
- 更隐蔽的传导链：全项目无 `TaskScheduler` 配置，Spring Boot 2.7 默认调度线程池大小为 1，本类 8 个任务共用一线程；清理任务一旦长时间占用，每 6 秒的理智刷新、每 5 秒的设备离线监控全部停摆，而设备监控靠"每次递减"推进计数，停摆会触发 `num == -60` 分支，误报设备离线并向管理员推送告警。
- 对策：(a) 分批删除，用 MyBatis-Plus 的 `last("LIMIT n")` 在 delete 上追加批次上限，循环执行直到影响行数为 0，并限制单轮最大批次数/耗时，超出留待下一轮；(b) 为 `log.time` 补索引；(c) 可选地为调度器显式配置线程池，使慢任务不再阻塞高频巡检。

**P2 中危：异常堆栈**

- `log.error("...{}", e.getMessage())` 未传异常对象，改为 `log.error("【日志清理】 执行失败", e)`。
- 说明：本文件前 7 个任务均无 try/catch，新增兜底属于与既有风格的"良性偏离"，只需修正日志写法，不必移除。

**P3 低危：cron 健壮性与风格**

- `new CronTrigger(logCleanCron)` 在注册期执行，非法或空 cron 会直接导致应用启动失败；而 `@Value` 对"已定义但为空"的环境变量返回空串而非默认值。需在注册前校验并给出可读提示，非法时回退到默认 cron。
- 顺手删除新增代码块中 Runnable lambda 与 Trigger lambda 之间多出的空行，与其余 7 个任务对齐。

**可测性**

- 把清理逻辑从 lambda 中抽成可见方法，便于补单元测试覆盖边界值（0 天、负数、正常值、超大批次提前退出）。

## 实现注意事项

- **热路径与瓶颈**：`log` 表写入极频繁（`LogServiceImpl.logInfo/logWarn/addLog` 被各巡检任务高频调用），禁止任何全表扫描式删除；分批大小需同时受"单批条数"与"单轮批次上限"双重约束。
- **事务边界**：分批删除每批独立提交，不要加 `@Transactional`，避免长事务锁表。
- **SQL 注入**：`last()` 只允许传入内部常量或经白名单校验的整数，禁止拼接外部输入。
- **日志**：失败日志必须传完整异常对象；成功日志在循环结束后汇总输出一次（总条数 + cutoff），避免每批一行造成日志刷屏。
- **爆炸半径控制**：默认值改为关闭属于行为变更，需同步更新 `.env.example` 说明；不改动既有 7 个任务；不加新依赖；不加全局逻辑删除配置。
- **索引落地风险**：需先确认 actable 1.5.0 是否提供索引注解，若支持则优先用注解；大表 DDL 需评估锁影响，MySQL InnoDB 加二级索引通常可在 INPLACE/无锁模式下完成，但仍应在低峰期执行并保留回退方案。若注解方案不可行，则在部署文档中提供独立的 `ALTER TABLE` 迁移语句。
- **多实例备注**：项目为内存态架构（`DynamicInfo` 内存队列、`config/data.json` 落盘），隐含单实例假设；若多实例部署，各实例会并发清理同一区间，需在部署文档注明或引入分布式锁。

## 架构设计

本次为收敛式修改，不改变现有分层与调用关系，仅调整 `DynamicScheduleTask` 内部实现：

```
配置层  .env / application.yml (inquisition.log.clean.*)
           ↓ @Value 占位符链
调度层  DynamicScheduleTask.configureTasks()  —— 第 8 个 addTriggerTask
           ↓ 触发
业务    cleanExpiredLogs()  ← 新增可测方法（分批循环 + 边界校验）
           ↓
数据层  LogMapper (BaseMapper)  →  DELETE ... WHERE time 小于 cutoff LIMIT n
```

与既有 7 个任务完全同构，无新增组件、无新增抽象。

```java
@Value("${inquisition.log.clean.enabled:false}")

@Value("${inquisition.log.clean.retention-days:30}")

```

新增可测方法（供任务体调用与单元测试直接验证）：

```java
/**
 * 分批物理清理过期日志。
 * 前置条件：retentionDays 必须大于 0，否则记录警告并返回 0，不执行任何删除。
 * 执行方式：按批次循环删除早于截止时间的记录，达到单轮批次上限或耗时上限即停止，
 * 剩余部分留待下一轮调度，避免长事务与长时间独占调度线程。
 *
 * @return 本轮实际删除的总条数
 */
int cleanExpiredLogs(int retentionDays, int batchSize, int maxBatches);
```

单元测试需覆盖的用例：retentionDays 为 0 和负数时零删除且不调用 mapper；正常值时按批循环并在批次耗尽后停止；mapper 抛异常时被捕获且不影响后续调度。
